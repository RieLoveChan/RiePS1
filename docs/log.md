## 2026-07-15
* **Correction**: Read the raw contents of `DAT_80105120`'s three function-pointer tables (`tools/ghidra/scripts/DumpJumpTable.java` against `0x800d9abc`) and found exactly 45 valid code-address entries (`45 = 15 x 3`, an enter/update/exit triple for 15 states), terminated by `0xFFFFFFFF` -- not 42. This refutes the earlier same-day claim that `DAT_80105120` directly indexes the 42-entry screen-name string table (15 != 42); the two are more likely separate structures. The string table's own contents remain valid evidence for the screen names it lists -- only the "what indexes it" claim is withdrawn. A more conservative reading is that the 42-name table is a debug/test-mode menu listing rather than the engine's live state enum. Bonus: found a further, unexplored table of option/settings-name strings ("Game Mode", "Diet Mode") immediately after the 45-entry table's terminator.
* **Discovery**: Found a 42-entry screen-name string table at `0x8001bb10` (`BOOT`, `PREPARE`, `INTRO`, `HOW TO`, `DANCING`, `STAGE END`, `RESULT`, `NON STOP I/C`, `STYLE SEL`, `MODE SEL`, `CHARA SEL`, `MUSIC SEL`, `SEQKIND SEL`, `LINK SEL`, `COURSE SEL`, `INRAN SEL`, `EDSEQ_SEL`, `SELECT END`, `NAME ENTRY`, `PRE_END`, `ENDING`, `URL&PASS`, `LINK START/END`, `GAME_OVER`, `PLAY START`, `GAME ??`, `PUSH START`, `WARNING`, `KONAMI`, `BEMANI`, `TOSHIBA`, `TMOVIE`, `TITLE`, `CATCH DEMO`, `PLAY DEMO`, `RANKING`, `LETS LINK`, `DEMO ??`, `TEST_MODE`, `OTHER`) while chasing `FUN_80049dec`'s `"TEST_MODE"` string, using a new tool, `tools/ghidra/scripts/DumpBytes.java` (raw hex+ASCII dump). This is almost certainly the game's real top-level screen enum, indexed by `DAT_80105120` through three parallel function-pointer tables (update/exit/enter) -- a much richer state machine than the `PTR_DAT_800ac8e8` mode/submode system this document has focused on so far. Directly confirms the repository owner's domain-knowledge account with literal string evidence: `WARNING`=Caution, `KONAMI`/`BEMANI`/`TOSHIBA`=three separate Company logo screens, `HOW TO`=How To Play, `PLAY DEMO`=Gameplay Demonstration, `RANKING`=Ranking. One confirmed link to the existing mode system: mode `0x04` initializes `DAT_80105120` to state 0 (`BOOT`); mode `0x02`/submode `0x02` pumps it every frame. How the two systems fully relate is not yet established -- likely the next major thread, possibly meriting its own `DAT_80105120`-keyed screen-flow document.

Submode `0x02` (`FUN_80049dec`) turned out unrelated -- a separate enter/exit/update state machine keyed on `DAT_80105120` (shared with mode `0x04`'s music-database loader) that copies a table ending at an entry containing a pointer to the literal string `"TEST_MODE"`, this project's first human-readable string. Every mode reviewed in the `0x00 -> 0x10 -> 0x04 -> 0x02` chain now reads as infrastructure (memory card I/O, GPU reset, asset/database loading, resolution switching), not a visible screen -- the first real attract-loop screen identity is still further down the chain, not yet located.
* **Review**: Reviewed mode `0x04`'s remaining 6 callees, completing its call tree. * **Review**: Reviewed `FUN_800232cc`'s (mode `0x10`/submode `0x00`) two callees, `FUN_800222fc` and `FUN_8002a9dc`. Neither touches submode (the "does the menu get armed during boot" question stays open), but both clarify what this submode is for: `FUN_800222fc` is pure GPU reinitialization built from real PsyQ calls (`ResetGraph`/`GsInitGraph2`/`GsInit3D`/`InitGeom`/`ClearImage2`/`DrawSync`); `FUN_8002a9dc` (called from 22 places project-wide, confirming it's generic) is an asset loader that draws primitives then uploads images to VRAM via the real `LoadImage` call. * **Review**: Reviewed mode `0x10`'s two submode handlers to test the "is mode 0x10 the Company screen?" hypothesis from earlier the same day. Refuted it: `FUN_80022b30` (submode `0x01`) is a real d-pad-cycle-and-confirm menu with a 3-entry destination-mode lookup table (`DAT_800ac8e0 = {4, 0x32, 0x20}`, read directly with a new tool, `tools/ghidra/scripts/DumpShorts.java`), not passive splash-screen code -- a non-interactive attract-loop screen wouldn't need selection logic across 2 controller ports. New hypothesis: mode `0x10` is a title/mode-select hub, `suspected`. This also closes the loop on the confirmed transition graph: mode `0x10` <-> modes `0x20`/`0x32` (menu choices 1/2 send you there, their handlers send you back), while submode `0x00` (`FUN_800232cc`) always unconditionally forwards to mode `4` (which itself flows to mode `2`). `FUN_800232cc` also reaches a second real PsyQ kernel call, `SetDispMask(1)`. New open question: since `SetMode` always resets submode to 0, and submode 0 always forwards away immediately, it's unclear how submode ever advances to 1 to show the menu at all.
* **Tooling + review**: Added `tools/ghidra/scripts/DumpFieldXrefs.java` (dumps decompiled C for every function referencing a given global) and used it on `PTR_DAT_800ac8e8` (58 referencing functions) to chase the long-open "where is the mode field (+0x28) ever written" question. Found `FUN_80023210` is the game's sole `SetMode(newMode)` primitive: writes its argument to +0x28 and clears submode (+0x2a) plus two previously-unseen fields (+0x2c/+0x2e). This turns every already-reviewed call site to it into a confirmed mode transition (modes 0x00/0x20/0x32 -> 0x10; mode 0x04 -> 2; any mode -> 0x80 via the dispatcher's own epilogue flag), resolves that open question, and refutes the earlier +0x17-as-queued-next-mode hypothesis (superseded, not deleted) since the function that writes +0x17=0x80 separately calls SetMode(0x10), not 0x80. New hypothesis: mode 0x10, reached by 3 independent transitions and the default fallback, is a structural match for **Company** (the attract loop's anchor screen) -- recorded at `suspected`. Also surfaced `FUN_80021374`, a second +0x28 read site outside the mapped dispatcher tree, not yet reviewed.
